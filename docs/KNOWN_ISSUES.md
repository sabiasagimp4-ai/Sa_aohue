XDoG(線検出)とブラーを中心に、実測で確認できた問題をまとめる。あわせて調査中に判明した性能・ホスト間乖離・テスト体制の問題も記載する。
README 7章の「残っている問題」が定性的な一覧なのに対し、この文書は **数値と再現手順を伴う欠陥リスト** として扱う。

## 再現方法

```bash
python3 tests/xdog_study.py                       # 1章の検出器の測定 (NumPy必要)
g++ -std=c++17 -O2 -pthread -ffp-contract=off -I. -o hotspot tests/hotspot_study.cpp && ./hotspot   # 2-3章
```

## 1. 線検出 (XDoG)

### 1-1. 現行実装は DoG ではない 【重大 / 未着手】

**症状**: 「Difference of Gaussians」と説明されている処理が、実際には2つのガウシアンの差になっていない。

**原因**: `src/core.h:192` の `discKernel(1.f)` を展開すると **中心1タップ(重み1.0)だけ** になる。`(±1,0)` は `rn2 == 1` でアンチエイリアス重みが `(1−√1)×1 = 0` となり `if(aa<=0) continue` で捨てられるため。したがって小さい側のσは0、すなわち恒等写像である。実際に計算されているのは:

```
dog = L(x) − (9タップpillbox平均)      ← 小さい側にローパスが無い
```

`discKernel(1.6)` の9タップ(中心1.0 / 辺0.6×4 / 角0.185787×4、合計4.143)は等価σ約0.685のpillboxである。つまり全体として **固定3×3のアンシャープ・ハイパス1枚** に相当する。YMM版 `ymm/Shaders/LineMask.hlsl` の `disc(p,1.0)` も同じ理由で中心1タップになり、同一の挙動である。

**影響**: 小さい側にローパスが無いため、入力ノイズが減衰なしでそのまま `dog` に入る。1-2 の誤検出の直接の原因。

**解決策**: 小さい側を実ガウシアンにする。1-2 の測定の通り、これ単独で誤検出が桁で減る。

---

### 1-2. 実素材のノイズで平坦部の6割を線と誤検出 【重大 / 未着手】

**症状**: PIPELINE 5章の「平坦に見える背景領域にも薄いCavityが乗る」という既存の観察。今回これを定量化した。

**測定**: 線は0.2暗い1〜2px幅を0/30/45/63°に配置。背景ノイズはPIPELINE 5章で `image.png` の平坦部から実測された標準偏差0.035。誤検出率は既定しきい値0.015を平坦部が超えた画素の割合。

| 検出器 | 線応答 | 平坦部1σ | SNR | 誤検出率 |
|---|---:|---:|---:|---:|
| 現行 (恒等 − pillbox1.6) | 0.07818 | 0.02853 | 2.7 | **59.99%** |
| XDoG σ=0.6 | 0.03776 | 0.00979 | 3.9 | 12.48% |
| XDoG σ=1.0 | 0.03020 | 0.00515 | **5.9** | 0.33% |
| XDoG σ=1.6 | 0.02340 | 0.00317 | **7.4** | 0.00% |

ノイズを0.07に上げると現行の誤検出率は79%になる。

**影響**: ノイズを含む実写素材では、線とは無関係な領域にマスクが立ち、そこに彩度増幅が掛かる。`Line Threshold` を上げれば減るが、それは弱い本物の線も同時に捨てる操作であり、根本対処にならない。

**解決策**: 1-1 の通り小さい側を実ガウシアン化する。σ=1.0で誤検出60%→0.33%、SNR 2.7→5.9。σは新パラメーター `Line Scale` として露出する(`docs/FEATURE_PROPOSALS.md` 4章)。

### 1-3. 線の向きで応答が57%変わる 【中 / 未着手】

**症状**: 同じ強さの線でも、斜めか水平・垂直かでマスクの濃さが変わる。

**測定**: 1px幅の理想エッジを0〜90°回転させたときの最大応答。

| 検出器 | 0° | 45° | 角度による振れ幅 |
|---|---:|---:|---:|
| 現行 | 0.11725 | 0.18966 | **57.1%** |
| XDoG σ=0.6 | 0.08611 | 0.09908 | 33.3% |
| XDoG σ=1.0 | 0.09323 | 0.10490 | 16.8% |
| XDoG σ=1.6 | 0.10413 | 0.10329 | **2.6%** |

**原因**: 3×3のpillbox(実質的に十字+角の粗い近似)は等方的でない。ガウシアンは連続領域で等方だが、σが小さいほど格子への標本化で異方性が残る。

**影響**: 建物の水平垂直線と、斜めの輪郭とで効果の強さが1.6倍違う。しきい値では補正できない。

**解決策**: 1-1 と同じ。σを上げるほど改善する(σ=1.6で2.6%)。

---

### 1-4. しきい値レンジが現行検出器の振幅に固定されている 【中 / 未着手】

**症状**: `Line Threshold` の 0〜100 → 0〜0.03 という写像は、現行カーネルの応答振幅を前提にした値である。

**測定**: 理想ステップに対する応答スケール(カーネルの正ローブL1ノルム)。

| 検出器 | 正ローブL1 | 現行比 |
|---|---:|---:|
| 現行 | 0.75864 | 1.000 |
| XDoG σ=0.6 | 0.30594 | 0.403 |
| XDoG σ=1.0 | 0.34446 | 0.454 |
| XDoG σ=1.6 | 0.32560 | 0.429 |

**影響**: 検出器やσを変えると、同じスライダー位置の意味が約2.2倍ずれる。σ可変化(`Line Scale`)を入れると、σを動かすたびにしきい値を取り直す必要が生じる。

**解決策**: `dog` をカーネルの正ローブL1で正規化してからしきい値と比較する。こうすればスライダーの意味が検出器間・σ間で共通になる。

### 1-5. XDoG の τ<1 は絶対しきい値と両立しない 【設計上の注意 / 未着手】

**症状**: XDoG本来の定式化 `D = G_σ − τ·G_kσ` で τ<1 にすると、平坦部に `(1−τ)·L` のバイアスが乗る。

**測定**: 完全に平坦(ノイズ無し)な面に対する `D` の平均値。

| 輝度L | τ=1.0 | τ=0.99 | τ=0.98 | τ=0.95 |
|---:|---:|---:|---:|---:|
| 0.3 | 0.00000 | 0.00300 | 0.00600 | 0.01500 |
| 0.8 | 0.00000 | 0.00800 | **0.01600** | 0.04000 |
| 1.0 | 0.00000 | 0.01000 | 0.02000 | 0.05000 |

τ=0.98・L=0.8 で 0.016 となり、**線が1本も無くても既定しきい値0.015を超える**。符号は正なので、`Invert Lines` 側では明るい面全体が線になり、非反転側では明部の線が消える。1-2の表で τ=0.98 の誤検出率が0.33%→17.02%へ悪化するのはこれが原因。

**解決策**: (a) τ を1.0固定にして φ(ソフトしきい値)だけ採用する、または (b) しきい値を `D/G_kσ` のような相対量にする。**当面 (a) を推奨** — τ の絵作り上の役割は `Contrast` のガンマ補正が部分的に担っているため。

---

### 1-6. float32 の桁落ち 【非問題 / 調査済み】

τを1へ近づけると `G_σ − τG_kσ` が近い値どうしの引き算になるため精度劣化を疑ったが、実測では問題にならなかった。

| τ | \|D\|最大 | ぼかし2枚を引く | カーネルを先に合成 |
|---|---:|---:|---:|
| 1.0 | 3.27e-2 | 2.6e-7 | 3.6e-8 |
| 0.98 | 4.30e-2 | 2.8e-7 | 3.9e-8 |
| 0.999 | 3.33e-2 | 2.7e-7 | 3.5e-8 |

しきい値スライダーの1目盛(3.0e-5)の約1/100に収まる。**カーネル融合による精度対策は不要**であり、可分ガウシアン2回(O(r)/軸)を選んでよい。現行の非可分な円盤カーネル O(r²) より速くなる。

## 2. ブラー

### 2-1. Radius 1.00〜2.59 が同一出力になる 【重大 / 未着手】

**症状**: `Radius` スライダーの下端が効かない。

**原因**: `src/core.h:169` の `fastBlurInPlace` が `int r = max(1, round(radius/√3))` で整数量子化する。3回box passの合成σは `√(r(r+1))`。

| Radius | box r | 実効σ |
|---:|---:|---:|
| 1.00 | 1 | 1.414 |
| 2.00 | 1 | 1.414 |
| 2.50 | 1 | 1.414 |
| 2.60 | 2 | 2.449 |
| 4.00 | 2 | 2.449 |
| 6.00 | 3 | 3.464 |
| 24.00 | 14 | 14.491 |

**影響**: Radius 1.00〜2.59 は完全に同じ出力。実効σは1.414未満を表現できない。σが1に近い細い効果が作れず、さらに **XDoG の小σ側(σ=0.6〜1.0)を既存の `fastBlur` で代用できない**。UIは0.1刻みだが、実際に絵が変わる境目は Radius ≈ 0.87 / 2.60 / 4.33 / 6.06 … と粗い。

**解決策**:
1. XDoG の小σ側は専用の小カーネル可分ガウシアン(直接畳み込み、2×(2⌈3σ⌉+1)タップ)を用意する。半径が小さいのでコストは無視できる。
2. `Radius` 側の量子化は Kovesi の拡張box blur(幅の異なる2種のboxを混ぜて実効σを連続にする手法)で解消できる。既定値の出力が変わるためCIのビット比較の再ベースラインが必要。
3. 最低限の対処として、σとRadiusの関係(`σ = √(r(r+1))`, `r = round(Radius/√3)`)をUIの説明とREADMEに明記する。

### 2-2. AE版とYMM版でブラー幅が最大2.45倍違う 【中 / 未着手】

**症状**: 同じ `Radius` を指定しても、ホストによってぼけ幅が違う。`ymm/README.md` は「ピクセル単位の完全一致は保証しません」と書いているが、実際の差は小Radiusで想定よりはるかに大きい。

**測定**: AE側は `√(r(r+1))`、YMM側は `GaussianBlur.StandardDeviation = max(0.1, Radius/√3)`。

| Radius | AE 実効σ | YMM σ | 比 (AE/YMM) |
|---:|---:|---:|---:|
| 1 | 1.414 | 0.577 | **2.449** |
| 2 | 1.414 | 1.155 | 1.225 |
| 3 | 2.449 | 1.732 | 1.414 |
| 6 | 3.464 | 3.464 | 1.000 |
| 24 | 14.491 | 13.856 | 1.046 |
| 512 | 296.500 | 295.603 | 1.003 |

**原因**: AE側が `r` を整数へ丸めた上で `σ=√(r(r+1))` になるのに対し、YMM側は `Radius/√3` をそのままσとして渡している。Radius≥6ではおおむね一致するが、下端では乖離する。

**解決策**: どちらかに合わせる。推奨はYMM側の式(`Radius/√3`)ではなく、**両者とも「Radius が実効σを意味する」定義に統一する**こと。AE側は `r = round((−1+√(1+4σ²))/2)`、YMM側は `StandardDeviation = Radius` とする。2-1 の量子化解消と同時に行うのが自然。

### 2-3. running sum の float32 累積誤差 【低〜中 / 未着手】

**症状**: box passの prefix sum を float32 で画像幅ぶん累積するため、大きな数どうしの引き算になり精度が落ちる。誤差は画像が広いほど、半径が小さいほど大きい。

**測定**: `fastBlurInPlace` 全体(H/V 3往復)を倍精度の同一式と比較。入力は `lineArt` が実際にぼかす二値マスク。

| 解像度 | Radius | 最大絶対誤差 | 8bit1階調比 | 16bpc1階調比 |
|---|---:|---:|---:|---:|
| 1920×1080 | 6 | 2.45e-05 | 0.62% | 80% |
| 1920×1080 | 24 | 1.10e-05 | 0.28% | 36% |
| 3840×2160 | 6 | 5.41e-05 | 1.38% | **177%** |
| 3840×2160 | 24 | 3.48e-05 | 0.89% | 114% |
| 3840×2160 | 128 | 1.84e-05 | 0.47% | 60% |

**影響**: 8bpcでは不可視。16bpcでは4K・小Radiusでマスクが1〜2階調ぶんずれうる。マスクはこの後 `Contrast` のガンマと彩度増幅を通るため、誤差が拡大される場合がある。

**解決策**: prefix sum の累積のみ double にする(出力は float のまま)。O(n) は変わらず、追加コストは scratch のメモリ帯域のみ。あるいは一定間隔で累積をリセットするブロック化prefix sum。**この誤差はCIでは検出できない** — ビット比較は同じアルゴリズムのベースラインとの一致を見ているだけで、精度の基準を持たないため(5-1参照)。

### 2-4. YMM版のD2Dブラーは既定で近似モード 【要確認】

`GaussianBlur` の `Optimization` を明示しておらず、Direct2Dの既定は `BALANCED`。Microsoftのドキュメントによれば BALANCED は「比較的小さい半径でも事前スケーリングなどの内部最適化を適用」し、`QUALITY` は「近似が見えにくい大きな半径でのみ内部最適化を使う」。つまり現状は小〜中Radiusで内部的にダウンスケール近似が入りうる。

また `BorderMode` の既定は `SOFT`(外側を透明で埋める)。マスクはα正規化して読むため実質「範囲外を無視する」動作になり、AE版の `boxPass`(窓を切り詰める)と一致する。一方 **AE版の `discAt` は端画素を複製** するので、DoG段だけはAEとYMMで境界の扱いが違う(2-5参照)。

**解決策**: `Optimization = Quality` を明示する。実機で見た目の差を確認してから決める。標準偏差の上限はドキュメント上規定されていないため、Radius=512(σ≈296)が実用に耐えるかも実機確認が必要。

出典: [gaussian-blur.md (MicrosoftDocs/win32)](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/Direct2D/gaussian-blur.md)

### 2-5. AE版の内部で境界処理が不統一 【低 / 未着手】

`discAt` (`src/core.h:91`) は `std::clamp(x+tap.dx,0,w-1)` で **端画素を複製** する。一方 `boxPassInto` (`src/core.h:115`) は `lo/hi` を画像内へ切り詰めて **窓を狭める**。同じ `lineArt` の中で、DoG段と最終ブラー段の境界の扱いが違う。

**影響**: フレーム端1〜2画素の挙動。SmartFXで全画面チェックアウトしているため通常は影響が小さいが、タイル化(README 7章)を実装すると顕在化する。

**解決策**: どちらかへ統一する。マスクの意味(「線が無い領域は0」)からは窓の切り詰めが自然。

### 2-6. AEの解像度設定 (downsample) に追従していない 【中 / 未着手】

**症状**: AEのビューアを「1/2画質」「1/4画質」にすると、プレビューと最終出力で効果の見た目が変わる。

**原因**: `src/Sa_aohue.cpp` は `in_data->downsample_x/y` を一度も読んでいない。AEは低画質表示のとき縮小したフレームを渡すが、`Radius` と検出カーネルは画素単位のまま適用されるため、フレームに対して相対的に2倍・4倍広く効く。AEのプラグインは画素単位のパラメーターを `downsample_x.num/den` でスケールするのが約束事である。

**影響**: プレビューで詰めた設定が最終レンダリングで再現しない。プロキシ・ドラフト画質でも同じ。YMM4側もプレビュー解像度に対して同じ性質を持つ。

**解決策**: `render()` に入る時点で `radius` と検出σへ `downsample_x.num/downsample_x.den` を掛ける。非正方画素(`downsample_x != downsample_y`)は、当面どちらか一方(または幾何平均)を使うと決めて明記する。この対処は解像度非依存モード(`ideabyopus.md` A-2)の土台にもなる。

## 3. 性能

### 3-1. 1フレームの8〜9割が未計測・未並列の合成ループ 【重大 / 未着手】

**症状**: `docs/PERFORMANCE.md` は `lineArt` の最適化(1080pで2.64倍)を報告しているが、これは1フレームの一部でしかない。

**測定** (4論理CPU、mask>0が全画素の最悪ケース):

| 区間 | 1920×1080 | 3840×2160 | 並列化 |
|---|---:|---:|---|
| RGB→L 変換 (`render` 内) | 183.5 ms | 708.9 ms | **なし** |
| `lineArt` | 54.6 ms | 217.2 ms | あり |
| `Contrast` の pow ループ | 14.1 ms | 56.4 ms | **なし** |
| `chroma` 合成ループ | 601.0 ms | 2400.3 ms | **なし** |
| 合計 | 853.2 ms | 3382.8 ms | |
| PERFORMANCE.md の測定範囲 | 54.6 ms (**6%**) | 217.2 ms (**6%**) | |

PERFORMANCE.md自身が「RGB→L、最終の彩度/合成、SDKのチェックアウトを除く」と明記しているので嘘ではないが、**読者は2.64倍がフレーム全体の話だと受け取りやすい**。

**解決策**: `render()` の2つの画素ループを `parallelFor` に載せる。`PF_ABORT` はワーカースレッドから呼べないので、呼び出し側スレッドがチャンク境界で中断確認する形にする。合わせて PERFORMANCE.md に測定範囲の内訳表を追加する。

### 3-2. `chroma` 合成ループの具体的な改善余地 【重大 / 未着手】

1920×1080での測定(3案は累積):

| mask>0 の割合 | 現行 | +目標ゲインを先に試す | +リニアRGBの再利用 | +4スレッド |
|---:|---:|---:|---:|---:|
| 100% | 547.5 ms | 497.5 ms (1.10x) | 427.2 ms (1.28x) | 128.6 ms (**4.26x**) |
| 50% | 276.9 ms | 242.7 ms (1.14x) | 214.8 ms (1.29x) | 67.6 ms (4.09x) |
| 20% | 112.3 ms | 100.0 ms (1.12x) | 85.4 ms (1.32x) | 27.4 ms (4.10x) |

内訳の実体は超越関数である。1画素あたり sRGBデコードの `pow`×3 + `toLab` の `cbrt`×3 + 二分探索12回の `fromLab` + `encode` の `pow`×3。

**解決策**:
1. **並列化**(最大の効果)。
2. **リニアRGBの再利用**: `render()` は輝度場を作るためにすでに sRGB デコード済みなのに、`chroma()` が元画素から再度デコードしている。1画素あたり `pow`×3 の重複。
3. **目標ゲインを先に試す**: 3-3 参照。

なお 1-2 の誤検出問題があるため、実素材でも mask>0 の割合は高くなりやすく、上表の上の行に近い状況が起きうる。

### 3-3. 色域二分探索が色域内画素でも常に12回回り、しかも目標ゲインに届かない 【中 / 未着手】

**原因**: `src/core.h:56` の `chroma()` は `lo=1, hi=1+amount*mask` から必ず12回の二分探索を行う。目標ゲインが色域内でも探索を省略しない。しかも `lo` は `hi` に収束しきらないため、**色域内の画素にも目標より小さいゲインが適用される**。

| amount | mask | 目標ゲイン | 実際 | 不足 |
|---:|---:|---:|---:|---:|
| 1 | 0.25 | 1.25000 | 1.24994 | 0.0049% |
| 1 | 1.00 | 2.00000 | 1.99976 | 0.0122% |
| 3 | 1.00 | 4.00000 | 3.99927 | 0.0183% |

測定した素材では目標ゲインが色域内に収まる画素が51.2%あり、その全てで12回の `fromLab` が無駄になっている。

**YMM版はこの問題を持たない**: `ymm/Shaders/Composite.hlsl` の `adjustColor` は目標ゲインをまず試し、色域外のときだけ探索する。つまりこれは **AE版とYMM版の出力差(最大5.638e-04、8bitの1階調の約1/7)** でもある。

**解決策**: AE版をYMM版と同じ手順(目標ゲインを先に試す)に揃える。速度と正確さと一貫性が同時に改善する。`tests/check_native.py` のNumPy参照実装の更新が必要(`tests/check_performance.cpp` のビット比較は `smallDisc`/`boxPass`/`lineArt` のみを対象としており `chroma` は含まないため、CIは通る)。

---

### 3-4. Contrast=1 でも全画素に `pow` を掛けている 【低 / 未着手】

`src/core.h:202` の `for(auto& v:line) v=std::pow(unit(v),1/max(.1f,p.contrast));` は既定の Contrast=1 でも実行される。

**検証**: `pow(x, 1.0f) != x` となる例は200万サンプルで **0件**(IEEE 754の規定通り)。したがって Contrast=1 のときこのループを丸ごと省略しても **出力はビット単位で完全に一致する**。CIのビット比較を維持したまま 1080pで14ms、4Kで56msを削減できる。

**解決策**: `if(p.contrast != 1)` のガードを追加する。単一スレッドのままでも効果があり、リスクがない。

## 4. ホスト間の乖離

同名のエフェクトでありながら、AE版とYMM版で出せる絵が違う。

| # | 項目 | 状態 |
|---|---|---|
| 4-1 | 輝度・色相・自然な鮮やかさ・負のAmount が YMM版のみ | 未着手 (`docs/FEATURE_PROPOSALS.md` 提案C) |
| 4-2 | 色域探索の手順差による出力差 最大5.638e-04 | 3-3 参照 |
| 4-3 | ブラー幅が最大2.45倍違う | 2-2 参照 |
| 4-4 | DoG段の境界処理 (AE=端画素複製 / YMM=範囲外を無視) | 2-4, 2-5 参照 |
| 4-5 | `Line Threshold` の目盛が 0〜100 と 0〜255 で違う | 写像先はどちらも0〜0.03なので絵は一致する。設定値の共有・ドキュメントの共通化ができない点のみ |

**解決策**: 色調整の定義を `src/core.h` に一本化し、HLSL側をそれに合わせる(提案C)。ブラーとしきい値の定義も同時に揃える。

## 5. テストとCIの穴

### 5-1. ビット比較は「変化」を検出するが「精度」は検出できない 【構造上の問題】

`tests/run_portable.py` → `tests/check_performance.cpp` はベースライン `88ab06d` の `core.h` と出力を `memcmp` する。これは最適化が出力を変えていないことの強力な保証だが、**ベースライン自体が持つ誤差は永久に検出されない**。2-3 の累積誤差、1-1 の恒等カーネルは、どちらもCIが全て緑のまま存在していた。

**解決策**: ビット比較に加えて、**倍精度の独立実装に対する誤差上限** を持つテストを追加する(`tests/check_native.py` がNumPyでやっていることの `boxPass`/`fastBlur` への拡張)。ビット比較は回帰検出、精度テストは正しさ検証、と役割を分ける。

### 5-2. `PERFORMANCE.md` の測定範囲 【未着手】
3-1 参照。除外範囲は明記されているが、それが全体の94%を占めることは書かれていない。

### 5-3. `check-shaders.ps1` は LineMask の定数バッファ配置を検証していない 【低 / 未着手】
`Composite` については7つの定数のバイトオフセットを `fxc /dumpbin` で検証しているが、`LineMask`(`Threshold, Invert, Linear, Padding` の16バイト)は `SCENE_POSITION`/`TEXCOORD` の有無しか見ていない。C#側 `[CustomEffectProperty(PropertyType.Float, n)]` の並びとHLSLの宣言順がずれた場合、`LineMask` では検出できない。

### 5-4. AE実機での未確認事項 【要確認】
README 6章の通りAE本体での描画は未検証。特に以下は実機でしか確認できない。

- SmartRender経路で `in_data->output_origin_x/y` を使ってソースを索引している点(`src/Sa_aohue.cpp` の `render()`)。SmartFXでのこの値の扱いは実機確認が必要。
- 全画面チェックアウト(`req.rect` を ±1000000)時のホストの実際の供給範囲とメモリ挙動。
- `PF_OutFlag2_SUPPORTS_THREADED_RENDERING` を宣言していないためMFR(複数フレーム同時描画)が効かない。自前で最大16スレッドを使うため、宣言する場合はスレッド数の調整が必要。
- `src/Sa_aohue.cpp` の `my_version`/`out_flags` と `src/Sa_aohuePiPL.r` の `AE_Effect_Version`/`AE_Effect_Global_OutFlags` が二重管理になっている(現状の値は一致を確認済み: `32769` = `PF_VERSION(0,1,0,DEVELOP,1)`、`0x1400` = `SUPPORTS_SMART_RENDER|FLOAT_COLOR_AWARE`)。パラメーター追加時は両方の更新が必要。
