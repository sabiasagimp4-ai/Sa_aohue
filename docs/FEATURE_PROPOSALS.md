# 新機能提案 (2026-09-07)

対象は現行の2実装 — After Effects版 (`src/core.h`, `src/Sa_aohue.cpp`) と YukkuriMovieMaker4版 (`ymm/`) 。
既存の廃止経路 (MoGe-2+GTAO / Depth Anything V2) を復活させる提案は含めない。

## 0. 現状把握

両版とも処理の骨格は同じ「OKLab L → DoG (1.0px と 1.6px の円盤平均の差) → しきい値で二値化 → Radiusでぼかし → `^(1/Contrast)` → そのマスクでOKLab a/bを増幅」である。
違いはブラー実装 (AE版=3回box blur、YMM版=Direct2D Gaussian) と、YMM版だけに増えたカラー調整にある。

| UI | AE版 | YMM4版 |
|---|---|---|
| Amount / 量 | 0〜400% (既定100) | **-100〜400%** (既定100、負で無彩色化) |
| Radius / 半径 | 1〜512px (24) | 1〜512px (24) |
| Contrast | 0.1〜4 (1) | 0.1〜4 (1) |
| 輝度 (OKLab L) | **なし** | 0〜200% (100) |
| 色相回転 | **なし** | -180〜180° (0) |
| 自然な鮮やかさ | **なし** | 0〜100% (0) |
| Output Mode | Composite / Lines / Lines Inverted | 同左 |
| Invert Lines | あり | あり |
| Line Threshold | 0〜100 → 0〜0.03 (50) | 0〜255 → 0〜0.03 (128) |
| RGB Encoding | sRGB / Linear sRGB | 同左 |
| キーフレーム | AE標準 | `Animation` で全数値対応 |
| ブラー | 3回box blur (`fastBlurInPlace`) | D2D `GaussianBlur` (`Radius/√3`) |

つまり **同名のエフェクトが、ホストによって出せる絵が違う** 状態にある。これは提案Cの動機になる。

### 設計上の制約 (提案すべてに掛かる)

1. **既定値でのビット一致**: `.github/workflows/core-regression.yml` → `tests/run_portable.py` → `tests/check_performance.cpp` が、`lineArt` / `smallDisc` / `boxPass` の出力をベースライン `88ab06d` の `core.h` と **memcmpでビット比較** している。したがって新パラメーターは *既定値で従来と完全に同じ演算経路を通る* 設計にする必要がある (「既定値では新コードを通さない」分岐を明示的に置く)。
2. **AE本体未検証**: README 6章の通り、AEホスト上での実描画は未確認。以下はすべて実機確認を前提とした設計案である。
3. **AE版はCPU全画面チェックアウト**: `preRender` が全入力を要求する (`src/Sa_aohue.cpp` の `req.rect` を±1000000に設定)。近傍参照を増やす提案はメモリと再計算量にそのまま乗る。
4. **YMM版はステートレスなD2Dシェーダー**: フレーム間の状態を持てないため、時間方向の処理は原理的に不利 (提案G)。

## 1. 提案一覧

### A. 線スケール (Line Scale) — DoG半径の可変化 【優先度: 中〜高】

**現状**: DoGのカーネル半径は `src/core.h:192` の `discKernel(1.f)` / `discKernel(1.6f)`、YMM版は `ymm/Shaders/LineMask.hlsl` の `disc(p,1.0) - disc(p,1.6)` で固定。README 7章にも「固定値」と明記されている。

**課題**: 1px固定のDoGは解像度依存である。1080pで調整した設定を4K素材に当てると、線が相対的に太いため応答が落ち、逆に圧縮ノイズ・フィルムグレインの高周波にはよく反応する (PIPELINE 5章で `image.png` の平坦部に標準偏差9/255のノイズがあることを実測済み)。ユーザー側の対処が「`Line Threshold` を上げる」しかなく、これは *弱い線を捨てる* 操作なので、太い線を拾いたい要求には応えられない。

**提案**: `Line Scale` (0.5〜4.0、既定1.0) を追加し、DoG半径を `1.0×scale` / `1.6×scale` にする。

- `aohue::Options` に `scale=1` を追加、`lineArt` は `discKernel(p.scale)` / `discKernel(1.6f*p.scale)` を使う。`scale==1` は現行と同一の値になるので、CI のビット比較は既定値のまま通る。
- 厳密円盤平均は O(radius²)。scale=4 では 1タップあたり約130点×2になるため、**scale > 2 では 3回box blur (`fastBlur`) による近似へ自動切替**する案を併記する (新経路なので既定のビット一致には影響しない)。
- YMM版: `LineMask.hlsl` の `[unroll] for (-2..2)` を可変ループ化し、`Impl` に `Scale` プロパティを追加して `MapOutputRectToInputRects` の拡張量を `ceil(1.6*scale)+1` にする (現在は固定で3)。ここを直さないとタイル境界でクランプ由来の線が出る。

**未解決点 (先に測るべきこと)**: スケールを上げるとDoGの振幅そのものが小さくなるため、`Line Threshold` の意味が変わる。振幅をスケールで正規化するか、しきい値の再調整をユーザーに委ねるかは、実素材で応答曲線を測ってから決めたい。

### B. ソフトしきい値 (Line Softness) 【優先度: 高 / 最小コスト】

**現状**: `line[i]=(invert?dog>threshold:dog<-threshold)?1.f:0.f;` (`src/core.h:198`)。完全な二値化である。

**課題**: 二値化は (1) マスク境界がジャギる — 特に `Radius` が小さいとき、(2) **動画でチラつく** — `dog` がしきい値付近を上下する画素はフレームごとにON/OFFが反転する。現状これを緩和する手段は `Radius` を上げてぼかすことしかなく、効果の形自体を犠牲にしている。

**提案**: `Line Softness` (0〜100%、**既定0**) を追加し、0のときは現行の二値式をそのまま実行、>0 のとき `smoothstep(t-w, t+w, |dog側|)` によるソフト判定に切り替える。

- 既定0で従来コードパスをそのまま通すため、CIのビット比較は無改修で通る。
- コストは加算数個/画素。近傍参照は増えないので、メモリ・チェックアウト範囲に影響しない。
- 時間方向のバッファを持たずにチラつきを減らせる点が要点で、提案G (時間平滑化) より先に試すべき安価な代替になる。
- YMM版も `LineMask.hlsl` の `edgeMask` を同式にするだけで済む。
- テスト: `tests/check_native.py` の NumPy 参照実装に softness 付きケースを追加。`check_performance.cpp` は softness=0 のままベースライン比較を継続する。

### C. AE版へのカラー調整移植と `chroma()` の一本化 【優先度: 高 / 効果最大】

**現状**: YMM版だけが 輝度 (OKLab L)・色相回転・自然な鮮やかさ・負のAmount (無彩色化) を持つ (`ymm/Shaders/Composite.hlsl` の `adjustColor`)。AE版の `aohue::chroma` (`src/core.h:56`) は `if(amount<=0||mask<=0||!gamut(rgb)) return rgb;` で、彩度を上げることしかできない。

**課題**: 同じ製品名で出せる絵がホストごとに違う。しかも定義がC++とHLSLに二重管理されているため、片方だけ直る/ずれる事故が今後も起きる。

**提案**: 色調整の定義を `core.h` に一本化し、AE版へ4項目 (輝度・色相・自然な鮮やかさ・負のAmount) を移植する。

- `struct Look { float amount=1, brightness=1, hueShift=0, vibrance=0; };` と `chroma(RGB, float mask, const Look&, bool linear)` を追加。適用順は HLSL と同じ **L調整 → 色相回転 → vibrance重み付きゲイン → 色域内二分探索** に固定し、順序をコメントで明記する。
- 既存の `chroma(rgb,mask,amount,linear)` は `Look{amount}` へ委譲する薄いラッパーとして残す。`tests/check_native.py` / `check_ae.cpp` の既存アサーションは無改修で通る。
- AE UI: `Amount` の下限を 0 → -100 に広げ、`Brightness` / `Hue Shift` / `Vibrance` を追加。`src/Sa_aohue.cpp` の合成側早期リターン条件 (`mode==1&&(o.amount==0||...)`) は「amount==0 かつ brightness==1 かつ hueShift==0」に拡張が必要 — ここを直し忘れると新パラメーターが効かない。
- YMM版は最終的に `Composite.hlsl` を `core.h` と同じ式・同じ定数に揃える (現状 vibrance の基準彩度 0.4 がHLSL側にハードコードされている)。
- テスト: NumPy 参照に4項目を実装して比較。負のAmountでの色域二分探索は、探索区間が `[0,1]` 側になるので境界ケース (amount=-100%、mask=1) を明示的に追加する。

### D. 色相セレクター (Hue Range) 【優先度: 中】

**現状**: マスクが立っている画素の彩度を、色相に関係なく一律に増幅する。

**課題**: 「線が密なところを鮮やかに」だけだと、暖色の肌・木材まで一緒に持ち上がる。名前の通り青系だけを強調したい (`aohue`) といった用途に、現状はエフェクトを複製して色域キーで抜くしかない。

**提案**: `Hue Center` (0〜360°)・`Hue Width` (0〜180°、既定180=全域)・`Hue Falloff` を追加し、元画素のOKLab色相角から求めた重み (0〜1) をマスクへ乗算する。

- 既定 (Width=180) では重み恒等1 なので出力は変わらない。線検出側 (`lineArt`) には一切触れないため、CIのビット比較の対象外。
- 近傍参照ゼロ、per-pixelのみ。AE/YMM両方で同じ式を使える。
- **注意点**: 低彩度画素の色相角は数値的に不安定なので、`length(ab)` が小さい画素では重みを1へフェードさせる (=選択しない) 必要がある。これを入れないと平坦なグレー部でノイズが出る。

### E. マスク品質切替 (Mask Quality: Full / Half / Quarter) 【優先度: 中】

**現状**: マスクは常にフル解像度。`docs/PERFORMANCE.md` の実測で `lineArt` だけで 1080p 36ms / 4K 184ms、フル画面floatプレーンが4K時126MiB。

**課題**: 最終段で `Radius` (既定24px、最大512px) の大きなぼかしを掛けるため、マスクの高周波成分はどのみち捨てられている。それでも全画素でDoGと6回のbox passを回している。AEはCPU実行なので、プレビューの応答性に直結する。

**提案**: `Mask Quality` (Full / Half / Quarter、既定Full) を追加。Half/Quarter では 輝度場を valid重み付きbox平均で縮小 → 縮小解像度で `lineArt` → bilinearでマスクを拡大する。

- 期待効果: マスク計算量が約1/4・1/16、フル画面プレーンのメモリも同オーダーで減る (README 7章の「全入力チェックアウトはメモリと再計算量が増える」への部分的な回答)。
- 既定Fullで従来経路そのままなので、CIのビット比較に影響しない。
- **制約**: `Radius` が小さい (概ね4px未満) ときは縮小の影響が見えるため、その領域では自動的にFullへ落とすか、UI上で警告する。ここは実測してから決める。
- テスト: ビット一致ではなく、フル解像度マスクとの平均絶対誤差の上限で検証する (Radius別)。

---

### F. マスクのアルファ出力と適用範囲マスク入力 【優先度: 中 / 低コスト】

**現状**: `Output Mode` の Lines / Lines Inverted はRGBにマスク値を書き、アルファは元のまま (`write(output[x],{v,v,v},max)`)。

**課題**: 生成した線マスクを他のエフェクトへ渡すには、AE側でルミナンスキーを噛ませる必要がある。せっかく計算したマスクが使い回せない。

**提案**:
1. `Output Mode` に **`Mask to Alpha`** を追加 (RGB=白、アルファ=マスク)。AEのトラックマット、YMM4の合成にそのまま流せる。
2. AE版に **適用範囲レイヤー入力** (`PF_ADD_LAYER`) を追加し、そのレイヤーの輝度をマスクへ乗算する。YMM4側はホストのクリッピング機能があるため優先度は下がる。

いずれも線検出アルゴリズムに触れないため、既存テストへの影響がない。2 はレイヤー入力のチェックアウトが増えるので、`preRender` のチェックアウト処理とエラーパスの追加が必要 (未接続時は恒等)。

---

### G. 時間平滑化 (Temporal Smoothing) 【優先度: 低 / 提案は保留】

動画でのマスクのチラつきに対する本命の対処だが、AE版では `preRender`/`smartRender` で前後フレームの入力をチェックアウトする必要があり、全画面チェックアウトと組み合わさるとメモリが線形に増える。YMM版のD2Dシェーダーはフレーム間状態を持てないため、そもそも同等の実装ができず、両版の差がさらに開く。

**まず提案B (ソフトしきい値) を入れて、チラつきがどこまで減るかを実素材で測ってから判断すべき**、というのがここでの結論である。

## 2. 推奨する着手順序

| 順 | 提案 | 理由 |
|---|---|---|
| 1 | **B (ソフトしきい値)** + **F-1 (Mask to Alpha)** | どちらも既定値で恒等、近傍参照を増やさない、テスト改修が最小。チラつきとマスク再利用という実用上の不満に直接効く。 |
| 2 | **C (カラー調整の移植と一本化)** | ユーザーから見た価値が最大で、かつ2実装の乖離という構造的リスクを閉じられる。 |
| 3 | **A (線スケール)** | 効果は大きいがC++とHLSLの両方に手が入り、しきい値の意味の変化という要検証項目を抱える。 |
| 4 | **E (マスク品質)** / **D (色相セレクター)** | 性能と表現の追加。C・Aの後で、実測に基づいて判断する。 |
| 5 | G | B の結果を見てから再検討。 |

## 3. 今回提案に含めなかったもの

- **GPU化 (AE版)**: 効果は大きいが「新機能」ではなく実装基盤の入れ替えであり、まずAE実機での実測 (README 7章) が先。
- **タイル別halo付きROI**: 同上。提案Eがメモリ・時間の当座の緩和になる。
- **AI推論経路の復活**: 廃止判断 (README 8章) を覆す理由が現時点で無い。
- **HDR画素の彩度変調**: 現在は色域外画素を素通ししている。手を入れるなら作業色空間の扱い全体の設計が必要で、単独の機能追加としては切り出せない。
